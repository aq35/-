# 9. 私用の AI 指示文（コピペ用）

普段の作業で AI に貼り付ける指示文です。コードブロックの右上のボタンで、そのままコピーできます。`<...>` の部分だけ書き換えて使います。

- **英語版は [09-my-ai-prompts.en.md](09-my-ai-prompts.en.md)** です（同じ番号。長くならないよう、別ファイルに分けています）
- 補助コマンドの下の表の `‿` は、音がつながる場所です（[リンキングの解説](en-study/linking.md)）。指示文のコードブロックには入れていないので、そのままコピーできます
- 言語（Go・Rust など）に依存しない書き方にしています。コマンドは「このプロジェクトのフォーマッター・lint・テスト」と書き、AI に探させます
- 1 つの指示文で、頼むことは 1 つだけです
- 「コードを変更しない」「出力先のファイル」「分からないときは『不明』と書く」を、毎回明記しています

## 誤解されやすい言葉と、書き方

指示文では、次のように言い換えています。

| 普段の言い方 | 誤解される例 | 指示文での書き方 |
|---|---|---|
| 「属性を追加」 | 言語の「属性」（Rust の `#[...]`、Go のタグ）と取り違える | 「データの項目（構造体のフィールド）」と書く。タグや属性も別に確認させる |
| 「PR の Closed」 | マージされずに閉じた PR まで含める | 「マージ済みの PR だけ。マージされずに閉じたものは対象外」 |
| 「採用された指摘」 | 返信だけで修正がない指摘まで含める | 「指摘のあとに、その指摘に沿った修正コミットがあるもの」と基準を書く |
| 「調べて」 | 調べながらコードを直してしまう | 「コードは変更しない」と明記する |
| 「本番のコードは触らない」 | テスト用モジュールが同じファイルにある言語で、ファイルを編集できなくなる | 「テスト以外の部分を 1 行も変えない」 |
| 「テストを書いて」 | 失敗するテストを通そうと、本番コードを直してしまう | 「まだ実装前なので、失敗するのが正しい」と明記する |
| 「直して」 | 元から壊れているものまで直す | 「自分の変更が原因のものは直す。元から失敗していたものは報告だけ」 |
| 「関連箇所」 | 検索で見つかったものだけを挙げる | 「同名」と「名前は違うが似ているもの」に分けて探させる |

## 0. 共通ルール（毎回最初に貼る）

```text
【共通ルール】
- 日本語で回答してください。
- 事実（コードや文書で確認できたこと）と、推測を分けて書いてください。確認できなかったことは「不明」と書いてください。
- 根拠として、ファイルのパスと行番号を示してください。
- 依頼に書かれていない変更はしないでください。
- 次の操作は、私が指示するまで実行しないでください: コミット、push、ブランチやタグの削除、force push、履歴の書き換え、本番環境への操作、秘密情報の読み出し。
- 進められる部分は進めてください。分からないことは推測で進めず、最後にまとめて質問してください。

【このプロジェクトの前提】
- 言語: <Go / Rust など>
- GraphQL のスキーマは schema/（git サブモジュール）にあります。schema/ の中のファイルは変更しないでください。
- フォーマッター・lint・テストのコマンドは、必ずあります。分からないときは探してください（7 を参照）。
```

> 毎回貼るのが面倒な場合は、共通ルールを `CLAUDE.md`（リポジトリの直下）に書いておくと、Claude Code が自動で読み込みます。

## 1. 開発方針（マージ済み PR のレビュー指摘）

```text
過去の PR のレビュー指摘から、このリポジトリの「開発方針」を調べて、Markdown に整理してください。コードは変更しないでください。

【対象】
- リポジトリ: <owner/repo>
- マージ済みの PR だけを対象にします。マージされずに閉じた PR は対象外です。
- 期間・件数: <例: 直近 6 か月 / 直近 50 件>

【「採用された指摘」の基準】
次のどちらかを満たす指摘だけを「採用された」とします。
1. 指摘のあとに、その指摘に沿った修正コミットがある。
2. 指摘のスレッドが Resolved で、返信で修正に同意している。
どちらにも当てはまらない指摘は、「採用されなかった／不明」として別に分けてください。

【調べ方】
- gh コマンドで、PR の一覧・レビューコメント・コメント後のコミットを取得してください。
- 取得できないときは、その旨を書いて、私に取得方法を聞いてください。

【整理のしかた】
- 同じ趣旨の指摘は、1 つの方針にまとめてください。
- 方針ごとに、次を書いてください。
  - 方針（1 文。「〜する」「〜しない」の形）
  - 理由（レビューで述べられていたこと）
  - 良い例 / 悪い例（コードの抜粋は短く）
  - 根拠（PR 番号とコメントの URL。複数あれば全部）
  - 出現回数（何件の PR で指摘されたか）
- 1 件の PR にしか出ていない指摘は、方針にせず「単発の指摘」に分けてください。
- コメントに書かれていたこと（事実）と、あなたの解釈を分けてください。

【出力】
- ファイル: docs/policy/development-policy.md
- 構成: 概要 / 方針一覧（出現回数の多い順）/ 単発の指摘 / 採用されなかった指摘 / 調査の範囲と方法
```

手元で先にデータを集めたい場合（AI が `gh` を使えないとき）:

```bash
gh pr list --repo <owner>/<repo> --state merged --limit 50 --json number,title,url,mergedAt
```

```bash
gh api repos/<owner>/<repo>/pulls/<PR番号>/comments --paginate
```

```bash
gh api graphql -f query='query($o:String!,$r:String!,$n:Int!){repository(owner:$o,name:$r){pullRequest(number:$n){reviewThreads(first:100){nodes{isResolved isOutdated comments(first:10){nodes{body path url createdAt}}}}}}}' -f o=<owner> -f r=<repo> -F n=<PR番号>
```

> `--state merged` が「マージ済みだけ」の指定です（`--state closed` はマージされなかった PR も含みます）。`isResolved` は、スレッドが Resolved かどうかです。

## 2. 実装から仕様を調べる

```text
実装（コード）を読んで、<対象の機能・モジュール> の仕様を調べ、Markdown に書いてください。

【前提】
- 仕様の正は「今のコードの動き」とします。設計書や PR の説明は、この依頼では使いません。
- コードは変更しないでください。

【調べる内容】
- 目的（何のための機能か。コードから分かる範囲で）
- 入力（引数・リクエスト・型・制約・デフォルト値）
- 出力（戻り値・レスポンス・型）
- 処理の流れ（呼び出し順。関数名とファイルを示す）
- 分岐とエラー（どの条件で、どのエラーを返すか）
- 副作用（DB の更新、外部 API の呼び出し、ログ、キャッシュ）
- 暗黙の制約（認可、並び順、件数の上限、タイムアウト、リトライ）

【書き方】
- 各項目に、根拠のファイルパスと行番号を付けてください。
- コードから読み取れたことは「事実」、コードからは分からないこと（意図・背景）は「不明」と書いてください。推測で埋めないでください。
- 不自然な箇所（バグの疑い、コメントとコードの食い違い）は、仕様とは別に「気になった点」にまとめてください。

【出力】
- ファイル: docs/spec/<機能名>.md
```

## 3. 設計書から仕様を調べる

```text
今の設計書を読んで、<対象の機能> の仕様を Markdown に整理してください。

【対象の設計書】
- <パスまたは URL。例: docs/design/xxx.md>
- 指定がない、または見つからないときは、docs/ などを探し、どの文書を読んだかを書いてください。

【前提】
- 設計書に書かれていることだけを整理してください。コードは読まないでください（コードとの比較は、別の依頼で行います）。
- コードは変更しないでください。

【整理する内容】
- 目的 / 入力 / 出力 / 処理の流れ / エラー / 制約 / 非機能要件（性能・可用性・セキュリティ）

【書き方】
- 各項目に、設計書のどの章に書かれていたかを付けてください。
- 設計書の中の、矛盾している箇所・曖昧な箇所・未定（TBD）の箇所は、「要確認」として一覧にしてください。
- 設計書の更新日や版が分かれば、書いてください（内容が古い可能性を判断するため）。

【出力】
- ファイル: docs/spec/<機能名>-design.md
```

## 4. 今回やりたいことを仕様にする

```text
私の「やりたいこと」を、仕様に整理してください。コードは変更しないでください。

【やりたいこと】
<ここに自由に書く。箇条書きでよい>

【ルール】
- 私が書いていないことを、仕様に足さないでください。足したいことは「提案」の欄に分けてください。
- 意味があいまいな点は、仕様に書かず「確認したいこと」に質問として書いてください。
- 現状の仕様を確認する必要があるときは、関連するコードや設計書を読んでかまいません。読んだものは書いてください。

【仕様の構成】
1. 目的
2. 範囲（やること / やらないこと）
3. 入力と出力（型・制約・例）
4. 振る舞い（正常系 / 異常系 / 境界値）
5. 受け入れ条件（テストに書き換えられる形。「〜のとき、〜になる」）
6. 既存の動作への影響（変わるもの / 変えてはいけないもの）
7. 確認したいこと（質問）
8. 提案（私が書いていないが、あるとよいと思ったこと）

【出力】
- ファイル: docs/spec/<機能名>-next.md
- 書き終えたら、「確認したいこと」だけを私に提示して、回答を待ってください。
```

## 5. 今回の修正に関連する箇所を調べる

```text
今回の修正に関連する箇所を調べて、一覧にしてください。コードは変更しないでください。

【今回の修正】
<例: User に email（任意項目）を追加する>
（変更済みのときは、「現在のブランチの変更 = git diff origin/main...HEAD」を対象にしてください）

【言葉の意味】
- 「属性」は、データの項目（構造体のフィールド）のことです。言語の属性（Rust の #[...] など）やタグ（Go のタグなど）のことではありません。

【調べること】
1. 同じ型・関数・定数を使っている箇所（呼び出し元、使用箇所）
2. フィールド追加の対応漏れ
   - 構造体にフィールドを追加するときは、同じ構造体を使っている別の実装にも、同じフィールドが追加されている必要があります。
   - 次の 2 通りで探してください。
     a. 同じ構造体名を使っている実装
     b. 構造体名は違っても、フィールドの構成が似ている型（例: 変換元・変換先の型、API のレスポンス用の型、DB の行を表す型、GraphQL の型、テスト用の型）。フィールド名の一致や類似（snake_case と camelCase の違いも含む）を手がかりに探してください。
   - 見つけた型ごとに、「追加が必要か」を判断し、理由を書いてください。判断できないものは「要確認」としてください。
3. 項目に付随する設定（JSON などのタグ・属性、シリアライズの設定、バリデーション、デフォルト値）
4. 変換処理（型の変換関数、マッパー、手書きの詰め替え処理）
5. GraphQL のスキーマ（schema/）、DB のマイグレーション、テスト、ドキュメント、設定ファイル

【出力】
次の表で出してください。
| 場所（パス:行） | 型・関数 | 種別（同名 / 類似 / 呼び出し元 / 変換 / テスト / 文書） | 対応（要 / 不要 / 要確認） | 理由 |
- 「類似」で見つけたものは、似ていると判断した根拠（一致したフィールド名）を書いてください。
- 最後に、検索では見つけにくい箇所（リフレクション、マクロ、コード生成、文字列でのフィールド指定）の確認結果を書いてください。
```

手元で先に候補を探したいとき（`.` は検索する場所の指定で、省略できません）:

```bash
rg -n -i '\b<フィールド名>\b' .
```

```bash
rg -l -i '<フィールド名A>' . | xargs rg -l -i '<フィールド名B>'
```

```bash
rg -n -e 'type\s+\w+\s+struct' -e 'struct\s+\w+' --glob '*.go' --glob '*.rs' .
```

| EN | Search for the field name. |
|:---|:---|
| 読み | サーチ フォー ザ フィールド ネイム |
| つながり | なし（単語ごとに区切って読む） |
| JP | 1 つ目: フィールド名で検索する（`-i` は大文字小文字を区別しない） |

| EN | List files that contain both field names. |
|:---|:---|
| 読み | リス(ト) ファイルズ ザッ(ト) コンテイン ボウス フィールド ネイムズ |
| つながり | なし（単語ごとに区切って読む） |
| JP | 2 つ目: 2 つのフィールド名を両方含むファイルを探す（名前の違う似た型の候補） |

| EN | Find struct‿definitions. |
|:---|:---|
| 読み | ファイン(ド) ストラク‿デフィニションズ |
| つながり | struct‿definitions（同じ・似た子音が続く（前の音は言わない）） |
| JP | 3 つ目: 構造体の定義を一覧する（Go と Rust の書き方に対応） |

> `rg` は、検索する場所（`.`）を省略して、入力が端末でないとき（AI やスクリプトから実行したとき）は、標準入力を待って止まります。必ず `.` を付けます。

## 6. テストコードを書く

```text
今回やりたいことをもとに、テストコードを書いてください。

【今回やりたいこと】
<仕様のファイルのパス（例: docs/spec/xxx-next.md）、またはここに直接書く>

【変更してよいもの】
- テスト用のコードだけです（テストファイル、または同じファイルの中のテスト用の部分）。
- テスト以外の部分（本番のコード）は、1 行も変更しないでください。
- 既存のテストは、変更しないでください（追加のみ）。

【テストは 2 種類書きます】
A. 新しい仕様のテスト
- 仕様の振る舞いを確かめるテストです。まだ実装されていないので、実行すると失敗するのが正しい状態です。
- 失敗しても、本番のコードを直して通そうとしないでください。失敗の理由が「未実装のため」であることだけ確認してください。
- 各テストに、実装前であることを示す印を付けてください: 「未実装: <仕様の項目名>」（テストのスキップ機能の理由に書く。あとで検索できるようにするため）
B. 既存の動作を守るテスト（デグレの確認）
- 今の本番のコードの動作を確かめるテストです。今のコードで成功する必要があります。
- 今回の修正が影響しそうな箇所のうち、変えてはいけない振る舞いを対象にしてください。

【進め方】
1. まず、既存のテストをすべて実行し、結果を記録してください（元から失敗しているテストを区別するため）。
2. テストを書く前に、書くテストの一覧（A と B）を示して、私の OK を待ってください。
3. 書いたあと、すべてのテストを実行し、A と B に分けて結果を報告してください。
   - 期待は、A が失敗（またはスキップ）、B が成功です。期待と違う結果は、理由を説明してください。
4. 最後に、本番のコードを変更していないことを、git diff で示してください。

【書き方のルール】
- テストの置き場所と書き方は、既存のテストに合わせてください。
- テスト名は、何を確かめるかが分かる名前にしてください。
- 正常系・境界値（0 件・空・最大値）・異常系を含めてください。
- テストを通すために、期待値を弱める、テストを削除する、を行わないでください。
```

実装前のテスト（A）を探す・実行するコマンド:

```bash
rg -n '未実装:' .
```

|:---|:---|
| 読み | ファイン(ド) ザ テスツ マークト ナ‿リンプリメンティッド |
| つながり | not‿implemented（t＋母音（t がラ行に近い音になる）） |
| JP | 実装前の印が付いたテストを探す（実装できたら印を外す） |

```bash
git diff --stat
```

| EN | Show a summary of changes. |
|:---|:---|
| 読み | ショウ ア サマリ オヴ チェインジズ |
| つながり | なし（単語ごとに区切って読む） |
| JP | 変更したファイルを確認する（テスト以外のファイルが出ていないこと） |

## 7. フォーマッター・lint・テストを実行する

```text
フォーマッター・lint・テストを実行して、結果を報告してください。

【コマンドの見つけ方】
このプロジェクトのコマンドを、次の順で探してください。見つけたら、どのファイルで見つけたかを教えてください。
1. CI の設定に書かれているコマンド（例: .github/workflows/、buildspec/、パイプラインの定義）← これを正とします
2. タスクランナーや文書: justfile、Makefile、package.json の scripts、CLAUDE.md、README、CONTRIBUTING
3. 上記になければ、その言語の標準のコマンド
CI と手元でコマンドが違う場合は、CI のものを使ってください。

【手順】
1. 変更を加える前の状態（ベースライン）で、3 つを実行して結果を記録してください。
   - すでに変更してある場合は、今の作業ディレクトリを動かさずに、変更前の状態を別の場所に作って実行してください:
     git worktree add ../baseline origin/main
     （サブモジュールがあるときは git -C ../baseline submodule update --init も実行。終わったら git worktree remove ../baseline で消す）
2. 変更後の状態で、同じ 3 つを実行してください。
3. 失敗は、次の基準で扱ってください。
   - 今回の変更が原因の失敗（ベースラインでは成功していたもの）: 直してください。
   - ベースラインから失敗していたもの: 直さず、一覧にして報告してください。
   - フォーマッターの指摘: 自動整形で直してかまいません。ただし、今回の変更に関係のないファイルまで整形されたときは、そのファイルを元に戻して報告してください。
4. 直したら、3 つを再実行して、結果を報告してください。

【やってはいけないこと】
- lint の警告を、無効化の指定で黙らせる
- テストを、削除する・スキップする・期待値を書き換える
- コマンドの厳しさを下げて通す（警告をエラーにする指定を外す、など）
これらが必要だと思ったときは、実行せず、理由を説明して私に聞いてください。

【報告】
次の表で出してください。
| 種類（フォーマッター / lint / テスト） | 実行したコマンド | ベースライン | 変更後 | 備考（直した内容・元からの失敗） |
```

よくある例です（実際のコマンドは、CI の設定で確認します）。

| 言語 | フォーマッター | lint | テスト |
|---|---|---|---|
| Go | `gofmt -l .`（直す: `gofmt -w .`） | `go vet ./...` / `golangci-lint run` | `go test ./...` |
| Rust | `cargo fmt --check`（直す: `cargo fmt`） | `cargo clippy --all-targets -- -D warnings` | `cargo test` |

> この表のコマンドは、この環境では実行していません（Go の環境がないため）。表は、AI がコマンドを探すときの「見当」として使い、指示文の本文には書いていません。

## 8. 【提案】設計書と実装の食い違いを調べる

2 と 3 で作った 2 つの仕様を比べて、食い違いを洗い出します。設計書が古くなっていないかを確認できます。

```text
同じ機能について、設計書から作った仕様と、実装から作った仕様を比べて、食い違いを一覧にしてください。コードと文書は変更しないでください。

【比べるもの】
- 設計書から: docs/spec/<機能名>-design.md
- 実装から: docs/spec/<機能名>.md

【出力】
- ファイル: docs/spec/<機能名>-diff.md
- 次の表で出してください。
| 項目 | 設計書の内容 | 実装の内容 | 判定（一致 / 食い違い / 片方にしかない） | 根拠（設計書の章・コードのパスと行） |
- 「食い違い」と「片方にしかない」には、どちらが古そうか、あなたの見立てを「見立て」の欄に書いてください。断定はしないでください。
- 最後に、設計書を直す必要がありそうな点と、コードを確認する必要がありそうな点を分けて挙げてください。
```

## 9. 【提案】開発方針に照らして事前レビューする

1 で作った方針をもとに、PR を出す前に「過去に指摘された点」を先回りして確認します。

```text
今のブランチの変更を、開発方針に照らしてレビューしてください。コードは変更しないでください。

【対象】
- 変更: git diff origin/main...HEAD
- 開発方針: docs/policy/development-policy.md

【お願い】
- 方針の項目ごとに、今回の変更が「守っている / 破っている / 関係ない」のどれかを判定してください。
- 「破っている」は、該当するコードのパスと行番号、方針の項目、直し方の案を書いてください。
- 方針にない指摘（バグ、境界条件、エラー処理）があれば、別の欄に分けてください。
- 問題がなければ「問題なし」と書いてください。指摘を無理に作らないでください。
```

## 10. 【提案】完了前のセルフチェック

```text
作業の完了前に、変更が依頼の範囲に収まっているか確認してください。コードは変更しないでください。

【確認すること】
1. git status と git diff --stat で、変更したファイルの一覧を示してください。
2. 依頼に関係のない変更（整形だけの変更、無関係なファイル、生成物、設定ファイル、サブモジュールの指すコミットの変更）がないか確認してください。
3. 消し忘れがないか確認してください（デバッグ用の出力、一時的なコメントアウト、TODO、スキップしたテスト、秘密情報）。
4. 依頼した内容のうち、やっていないことがないか確認してください。
5. 7 の品質チェック（フォーマッター・lint・テスト）の結果が、すべて成功しているか確認してください。

【出力】
チェックの項目ごとに「OK / 要対応」を付け、「要対応」は該当するファイルと行を書いてください。
```

## 11. 【提案】作業の再開用

長い作業を中断して、あとで続きをするとき（新しい会話に貼るとき）に使います。

```text
ここまでの作業を、次の形で要約してください。新しい会話で作業を再開するために使います。

- 目的（何を実現しようとしているか）
- 決まったこと（仕様・方針・判断と、その理由）
- やったこと（変更したファイル、実行したコマンドと結果）
- まだやっていないこと（次の作業を、順番に）
- 未解決のこと・質問・リスク
- 確認できていない前提（推測で進めた部分）

事実と推測を分けて書いてください。
```

## 付録: `CLAUDE.md` の例（共通ルールを毎回貼らないために）

リポジトリの直下に `CLAUDE.md` として置くと、Claude Code が毎回自動で読み込みます。

```markdown
# 作業ルール

## 全般
- 日本語で回答する。
- 事実と推測を分ける。確認できなかったことは「不明」と書く。
- 根拠として、ファイルのパスと行番号を示す。
- 依頼にない変更はしない。
- 指示があるまで実行しない: コミット、push、ブランチ・タグの削除、force push、履歴の書き換え、本番環境への操作、秘密情報の読み出し。

## このプロジェクト
- 言語: <Go / Rust など>
- GraphQL のスキーマは schema/（git サブモジュール）。schema/ の中は変更しない。
- フォーマッター・lint・テストのコマンドは <例: justfile の fmt / lint / test>。CI と同じものを使う。

## 変更のあと
- フォーマッター・lint・テストを実行し、結果を報告する。
- 自分の変更が原因の失敗は直す。元から失敗していたものは直さず、報告する。
- lint の無効化、テストの削除・スキップ・期待値の書き換えは、しない。
```
