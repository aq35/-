# 8. AI への指示文テンプレート

AI（Claude Code など）に仕事を頼むときの指示文を、場面別にまとめました。コードブロックは右上のボタンでそのままコピーできます。`<...>` の部分を自分の内容に置き換えて使います。

## 1. 基本: 指示は 5 つの要素

```
 ① 目的 ──▶ ② 背景・前提 ──▶ ③ 制約 ──▶ ④ 完了条件 ──▶ ⑤ 確認方法
 何のため    今の状態         やらないこと  どうなれば終わり  どう確かめるか
```

| 要素 | 書くこと | 書かないとどうなるか |
|---|---|---|
| ① 目的 | 何を実現したいか（なぜ） | 手段が目的になり、的外れな修正になる |
| ② 背景・前提 | 今の状態、関連するファイル、使っている技術 | AI が推測で埋めて、実態と違う前提で進む |
| ③ 制約 | やらないこと、変えてはいけないもの | 頼んでいない変更（API の形、依存の追加）が混ざる |
| ④ 完了条件 | 何ができれば終わりか | どこで止めてよいか分からず、やりすぎるか途中で終わる |
| ⑤ 確認方法 | テストやコマンドで確かめる方法 | 「できたはず」の報告になり、検証されない |

**迷ったら ③ と ④ を足す**と、結果が大きく良くなります。

## 2. 万能テンプレート

日本語:

```
## 目的
<何を実現したいか。1〜2 文で>

## 背景・前提
- 現状: <今どうなっているか>
- 関連する場所: <リポジトリ・ディレクトリ・ファイル>
- 技術: Rust / GraphQL（schema はサブモジュール）/ AWS CodePipeline

## やること
1. <具体的な作業>
2. <具体的な作業>

## 制約（やらないこと）
- <例: 公開 API の形を変えない>
- <例: 依存ライブラリを追加しない>
- コミット・push・ブランチ削除・force push は、私が指示するまでしない

## 完了条件
- <例: cargo test が通る>
- <例: git diff に、依頼した範囲以外の変更がない>

## 進め方
- 最初に、調査結果と変更計画だけを報告してください。私が OK を出してから変更してください
- 分からないことは推測せず、質問してください

## 報告してほしい形
- 変更したファイルと、その理由
- 実行したコマンドと、その結果
- 確認できていないこと、リスク
```

English version:

```
## Goal
<What do you want to achieve? 1-2 sentences>

## Context
- Current state: <how it works now>
- Relevant places: <repo / directory / files>
- Stack: Rust / GraphQL (schema is a git submodule) / AWS CodePipeline

## Tasks
1. <concrete step>
2. <concrete step>

## Constraints (do NOT)
- <e.g. do not change the public API shape>
- <e.g. do not add new dependencies>
- Do not commit, push, delete branches, or force-push until I say so

## Definition of done
- <e.g. cargo test passes>
- <e.g. git diff contains no changes outside the requested scope>

## How to work
- First, report your findings and a plan only. Wait for my OK before changing anything
- If something is unclear, ask instead of guessing

## Report format
- Files changed and why
- Commands you ran and their results
- What you could not verify, and any risks
```

## 3. 場面別テンプレート

### 3-1. まず調べてもらう（変更はしない）

```
<機能・モジュール名> の仕組みを調べて、説明してください。
- ファイルは一切変更しないでください
- 処理の流れを、呼び出し順に図（テキスト）で示してください
- 根拠にしたファイルと行番号を、必ず併記してください
- 読んでも分からなかった点は「分からない」と書いてください
```

### 3-2. 機能を追加する

```
<機能の説明> を追加してください。

背景: <なぜ必要か>
入出力: <入力と期待する出力の例>

制約:
- 既存の公開 API（GraphQL のスキーマを含む）の形は変えない
- 変更は <ディレクトリ> の中に収める
- 依存ライブラリは追加しない

進め方:
1. 変更計画（変更するファイルと内容）を先に出してください。私が OK を出してから実装してください
2. 実装後、cargo fmt --check / cargo clippy -- -D warnings / cargo test を実行して結果を報告してください
3. テストも追加してください（正常系と、<エッジケース> の異常系）
```

### 3-3. バグを直す

```
次の不具合を直してください。

症状: <何が起きているか>
再現手順: <手順>
期待する動作: <本来どうなるべきか>
エラーや ログ: <貼り付け>

進め方:
1. まず再現するテストを書き、失敗することを確認してください
2. 原因（root cause）を特定し、根拠とともに説明してください。直すのはその後です
3. 原因に対する最小の修正にしてください（ついでの整理はしない）
4. 追加したテストが通ることと、既存のテストが壊れていないことを確認してください
```

### 3-4. コードレビューをしてもらう

```
次の変更をレビューしてください: <PR の URL / ブランチ名 / git diff main...HEAD>

観点:
- 正しさ（バグ、境界条件、エラー処理）
- Rust として自然か（所有権、unwrap の使い方、エラーの型）
- 後方互換性（GraphQL スキーマや公開 API を壊していないか）
- テストが足りているか

出力形式:
- 指摘は「必須」「推奨」「nit」の 3 段階に分けてください
- 各指摘に、ファイル名・行・理由・修正案を付けてください
- 問題がなければ「問題なし」とだけ書き、無理に指摘を作らないでください
```

### 3-5. リファクタリング

```
<対象> を整理してください（振る舞いは変えません）。

目的: <例: 重複をなくす／関数を分けて読みやすくする>
制約:
- 外から見た振る舞い（戻り値、エラー、ログ）を変えない
- 機能追加や仕様変更はしない
- 変更前後で cargo test が同じように通ること

進め方: 小さなステップに分け、各ステップでテストを実行して報告してください。
```

### 3-6. テストを追加する

```
<関数・モジュール> のテストを追加してください。
- まず現状のテストを確認し、足りない観点を挙げてください
- 正常系、境界値（0 件・最大値・空）、異常系を含めてください
- 本番コードは変更しないでください。テストしにくい箇所があれば、変更案だけ提示してください
- テスト名は、何を確かめるかが分かる名前にしてください
```

### 3-7. 設計を相談する（案を比較してもらう）

```
<課題> について、設計案を比較してください。まだ実装はしません。

前提: <規模、制約、期限、チームの人数>
お願い:
- 案を 2〜3 個出し、それぞれの利点・欠点・リスクを表で比べてください
- どれを推奨するか、理由とともに 1 つ選んでください
- 判断に必要な情報が足りなければ、先に質問してください
- 一般論ではなく、このコードベースの実態に基づいて答えてください（根拠のファイルを示してください）
```

### 3-8. スキーマ（サブモジュール）を更新して追従する

```
schema サブモジュールを最新にして、backend を追従させてください。

進め方:
1. git submodule update --remote schema を実行し、git diff --submodule=diff でスキーマの差分を見せてください
2. 破壊的変更（フィールド削除、型の変更、必須化）があれば、先に報告して止まってください
3. cargo build でコード生成と、コンパイルエラーの有無を確認してください
4. 生成された型に合わせて、リゾルバなどを修正してください
5. cargo test が通ることを確認してください

制約:
- schema 側のファイルは変更しない
- schema が、schema リポジトリの main にあるコミットを指していることを確認する（git -C schema merge-base --is-ancestor HEAD origin/main）
- コミットは、私が確認してから
```

### 3-9. 差分を確認して、PR の説明を書く

```
現在のブランチの変更を確認して、PR の説明文を書いてください。

1. git status -sb と git diff --stat origin/main...HEAD で、変更の全体を見せてください
2. 依頼した範囲に含まれない変更があれば、指摘してください
3. サブモジュールの指すコミットが変わっていれば、git diff --submodule=log の結果も載せてください
4. 説明文には「何を・なぜ・どう確かめたか・リスク」を書いてください
5. push や PR の作成は、私が OK を出してからにしてください
```

### 3-10. サブモジュールの衝突を解決する

```
git merge / rebase で、schema サブモジュールが衝突しています。解決してください。

進め方:
1. git status と git ls-files -u -- schema で、衝突の状況を見せてください
2. 3 つの候補コミット（base・ours・theirs）の内容を、git -C schema log で確認してください
   ※ rebase 中は ours と theirs が逆になることに注意してください
3. どのコミットを選ぶのが適切か、理由とともに提案してください。選ぶのは私です
4. 私が決めたら、git -C schema switch --detach <コミット> → git add schema で解決してください
5. cargo build && cargo test を実行して結果を報告してください

制約: merge --abort / rebase --abort や、履歴を書き換える操作は、私に確認してから。
```

### 3-11. 障害の原因を調べる

```
本番で次の障害が起きています。原因の調査を手伝ってください。

症状: <何が起きているか>
発生時刻: <いつから>
直近の変更: <直前のデプロイ・設定変更>

お願い:
- まず影響を抑える方法（ロールバックなど）を提案してください。実行はしないでください
- 原因の仮説を、可能性の高い順に挙げ、それぞれ「何を見れば確かめられるか」を示してください
- ログやコードを読んで確かめられた事実と、推測を分けて書いてください
- 本番環境に変更を加える操作は、一切しないでください
```

### 3-12. 用語や仕組みを教えてもらう（学習）

```
<用語・コマンド・概念> について、次の形式で教えてください。
- 一言で言うと何か
- 何のために使うのか（使わないと何が困るのか）
- 簡単な図（テキスト）
- 最小の実行例と、期待される出力
- よくある勘違いや失敗
- 英語の読み方（カタカナ）と、日本語訳
```

### 3-13. ドキュメントを書く・直す

```
<対象> のドキュメントを書いてください（または直してください）。
- 読者: <誰が読むか。前提知識はどの程度か>
- 目的: <読んだ人が何をできるようになるか>
- 実際に動かして確かめられるコマンドだけを載せてください。確かめていないものは「未確認」と書いてください
- 図は、テキストで簡単に
- 既存の文書の文体・見出しの付け方に合わせてください
```

## 5. 操作の線引き（どこまで任せるか）

| 区分 | 操作の例 | 頼み方 |
|---|---|---|
| **任せてよい** | ファイルを読む、検索する、`git status` / `git diff` / `git log`、`cargo build` / `cargo test`、ローカルでの実行 | そのまま頼む |
| **確認してから** | ファイルの編集、コミット、ブランチの作成、依存ライブラリの追加、push、PR の作成 | 「計画を出してから」「OK を出すまで push しない」 |
| **必ず人が判断** | `git push --force`、`git reset --hard`、ブランチやタグの削除、本番へのデプロイ、本番データの操作、秘密情報・トークンの扱い | AI には実行させず、**実行するコマンドの案だけ出させる** |

指示文に、次の 1 行を入れておくと安全です。

```
次の操作は、私が明示的に指示するまで実行しないでください: git push（特に --force）、git reset --hard、ブランチ・タグの削除、本番環境への操作、秘密情報の読み出し
```

### 確認チェックリスト

- [ ] `git status` に、想定外のファイルがない
- [ ] `git diff` が、頼んだ範囲に収まっている
- [ ] 新しい依存ライブラリや設定ファイルの変更が、勝手に入っていない
- [ ] テストが通る。**テストを消したり、期待値を書き換えて通していない**
- [ ] 「確認できていないこと」が報告に書かれている

## 7. 悪い指示 → 良い指示

| 悪い指示 | 何が問題か | 良い指示 |
|---|---|---|
| 「このバグ直して」 | 症状・再現・期待が不明。AI が推測で修正する | 症状、再現手順、期待する動作、ログを付け、「まず再現するテストを書いて」と頼む |
| 「いい感じにリファクタして」 | 範囲と基準がない。振る舞いが変わってもおかしくない | 対象、目的、「振る舞いを変えない」「テストが同じように通る」を書く |
| 「全部やっておいて」 | 範囲が広すぎて、確認できない | 小さく分け、「計画を出してから実装」を頼む |
| 「テストが通るようにして」 | テストを消す・弱める修正が起きうる | 「テストは変更しない。本番コードを直す」と明記する |
| 「最新の書き方で」 | どの版を指すのか不明 | 使うバージョン、参考にする既存コードを示す |
| 「速くして」 | 何を何秒にするのか不明 | 計測値（現状）と目標、測り方を書く |
